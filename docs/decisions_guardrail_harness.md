# เรื่องที่ต้องตัดสินใจ: Guardrail และ Harness

สถานะ: **ยังไม่ตัดสินใจ — ทุกข้อรอ Up2mEz** (ร่างเมื่อ 2026-10-08) · วันส่งงาน 2026-10-16
เอกสารนี้ไม่ใช่ข้อสรุป แต่เป็นรายการทางเลือก เหตุผล และข้อเสนอของผู้ร่างเพื่อให้ตัดสินใจครั้งเดียวจบ
หลังตัดสินแล้วให้บันทึกลง Decision Journal ใน `AI_AUDIT.md` โดยระบุเจ้าของการตัดสินใจ (Human / AI-suggested-Human-approved)

## 0. ใช้คำว่า guardrail และ harness ในความหมายนี้ (ถ้าไม่ตรง บอกให้ปรับ)

| คำ | ความหมายในเอกสารนี้ | ตัวอย่างในโปรเจกต์ |
| --- | --- | --- |
| **Guardrail** | กติกาที่บังคับด้วยโค้ด ไม่ใช่แค่เขียนใน prompt: ตรวจก่อน/หลังเรียก LLM แล้วปฏิเสธ แก้ หรือส่งต่อให้คน | ตรวจข้อมูลส่วนบุคคลในคำถาม, ปฏิเสธการวินิจฉัย, บังคับ citation, ตอบ "ไม่พบ" |
| **Harness** | โค้ดที่ห่อรอบ LLM และ retriever ให้ทำงานเป็นขั้นตอนที่ควบคุมและวัดผลได้: ลำดับขั้น, การเรียกเครื่องมือ, การบันทึก, และชุดทดสอบ/วัดผล | pipeline ถาม → ค้น → guard → ตอบ → ตรวจ; ชุดประเมิน (gold/silver, red-team, RAGAS) |

หลักจากสไลด์: ไม่มีกลไกเดียวที่พอ ต้องซ้อนหลายชั้น (`L11 p21` defense-in-depth;
`L13 p46` Constrain → Validate → Recover → Escalate) และงานเสี่ยงสูงต้องมีคนอนุมัติพร้อม audit log (`L13 p47`)

## 1. ข้อมูลที่ใช้ประกอบการตัดสินใจ (จาก corpus จริง)

- corpus v7: 68 เอกสาร, 3,873 หน้าเข้า index; **ไม่มีข้อมูลผู้ป่วยที่ระบุตัวได้** ยกเว้นเคสไม่ระบุชื่อ 1 ชุด (ดู `security_and_ethics.md` R3)
- ความเสี่ยงส่วนใหญ่อยู่ฝั่ง **ผู้ใช้พิมพ์ข้อมูลตัวเองเข้ามา** และ **ข้อความในเอกสารที่ถูกดึงเข้า prompt** ไม่ใช่ตัว corpus

- ผู้ให้บริการ LLM ตอบคำถามยังไม่เลือก (ทีมกำลังตัดสินใจเรื่อง API) ข้อ D1 ผูกกับเรื่องนี้

## 2. Guardrail — ที่ต้องตัดสินใจ

### G1. ถ้าคำถามมีข้อมูลส่วนบุคคล (ชื่อ, HN, เบอร์, อีเมล, เลขบัตร, ผลแล็บของตัวเอง) ควรทำอย่างไร

| ทางเลือก | ข้อดี | ข้อเสีย |
| --- | --- | --- |
| A. **ปฏิเสธ** ทั้งคำถามและขอให้พิมพ์ใหม่แบบไม่มีข้อมูลส่วนตัว | ปลอดภัยสุด ง่าย อธิบายง่าย | ผู้ใช้ที่พิมพ์ "ผม HbA1c 8.2" ถูกปฏิเสธโดยไม่จำเป็น |
| B. **Mask** ข้อมูลระบุตัว (ชื่อ/HN/เบอร์/อีเมล) แล้วตอบต่อ | ใช้งานได้ต่อเนื่อง | regex พลาดได้ โดยเฉพาะชื่อไทย; อาจทำให้ผู้ใช้เข้าใจว่าปลอดภัยแล้วทั้งที่ยังเหลือข้อมูลสุขภาพ |
| C. **เตือนแล้วให้ผู้ใช้เลือก** ส่งต่อหรือแก้ไข | ผู้ใช้ควบคุมได้ | demo ซับซ้อนขึ้น; ผู้ใช้อาจกดส่งต่อโดยไม่อ่าน |

ผู้ร่างเสนอ: **A สำหรับตัวระบุตัวตน (ชื่อ, HN, เบอร์, อีเมล, เลขบัตร) + B สำหรับตัวเลขสุขภาพส่วนตัว** (ปล่อยผ่านเป็นคำถามทั่วไปโดยไม่เก็บ)
เหตุผล: ตัวระบุตัวตนตรวจด้วยกฎได้แม่น (เลขบัตรมี checksum) ส่วนตัวเลขแล็บเดี่ยว ๆ ไม่ระบุตัวบุคคล · **ต้องตัดสิน:** ยอมรับระดับนี้หรือไม่
คำถามเปิด: ชื่อบุคคลไทยตรวจแม่นยากมาก จะยอมให้พลาดบางส่วนและระบุเป็นข้อจำกัดหรือไม่

### G2. บันทึกคำถามของผู้ใช้หรือไม่

| ทางเลือก | ผลต่อ PDPA | ผลต่อการประเมิน/ debug |
| --- | --- | --- |
| A. **ไม่บันทึกอะไรเลย** | เสี่ยงต่ำสุด | debug ยาก; แสดงผลซ้ำไม่ได้ |
| B. บันทึกเฉพาะ metadata (เวลา, จำนวน chunk, คะแนน, ผ่าน/ไม่ผ่าน guard) ไม่บันทึกข้อความ | ต่ำ | ดู pipeline ได้ แต่ไม่เห็นคำถาม |
| C. บันทึกคำถาม **เฉพาะชุดทดสอบของทีม** (gold/silver/red-team) ไม่บันทึกจากการใช้งานจริง | ต่ำ (ไม่มีข้อมูลบุคคลภายนอก) | วัดผลและทำซ้ำได้ครบ |

ผู้ร่างเสนอ: **B สำหรับ demo + C สำหรับการประเมิน** · ถ้าภายหลังให้คนนอกใช้และต้องเก็บแชท ต้องผ่าน consent และอาจารย์/EC/IRB ก่อน (`security_and_ethics.md` R10)

### G3. ขอบเขตที่ต้องปฏิเสธ (scope refusal)

ต้องตัดสินรายการที่ระบบจะ **ไม่ตอบ** แม้มีเอกสาร: การวินิจฉัยรายบุคคล, สั่ง/ปรับ/หยุดยาเฉพาะราย, แปลผลแล็บของผู้ใช้เป็นคำแนะนำเฉพาะราย, ภาวะฉุกเฉิน
สิ่งที่ต้องเลือก: (1) ปฏิเสธแล้วส่งต่อ "ปรึกษาแพทย์" หรือ (2) ตอบเฉพาะข้อมูลทั่วไปจากแนวทางพร้อมคำเตือน · และจะให้ข้อความฉุกเฉินแสดงเบอร์ 1669 หรือไม่
ผู้ร่างเสนอ: ใช้ (2) กับคำถามความรู้ทั่วไป และ (1) กับคำถามที่ขอให้ตัดสินใจแทนผู้ป่วยรายบุคคล โดยตรวจด้วยตัวจำแนกคำถามก่อนค้น (ต้องมีชุดทดสอบ)

### G4. "หลักฐานไม่พอ → ตอบว่าไม่พบ" ใช้เกณฑ์อะไร

| ทางเลือก | วิธี | ความเสี่ยง |
| --- | --- | --- |
| A. เกณฑ์คะแนนค้นคืน (score threshold) ปรับด้วย dev set | ง่าย วัดได้ | คะแนนของ dense, BM25, RRF ไม่เทียบกันตรง ๆ; ต้องปรับตามโมเดล |
| B. ให้ LLM ตัดสินว่า chunk ตอบคำถามได้หรือไม่ | จับกรณีกำกวมได้ | ช้า แพง; LLM เองอาจมั่นใจเกินจริง |
| C. A แล้ว B เฉพาะกรณีคะแนนกึ่งกลาง | สมดุล | ซับซ้อน |

ผู้ร่างเสนอ: **A ก่อน** วัดบนคำถามที่ "ไม่มีคำตอบใน corpus" ที่ทีมเตรียม; ถ้าผลไม่พอค่อยเพิ่ม B · ต้องตัดสิน: จะเตรียมคำถามกลุ่มนี้กี่ข้อ (ผู้ร่างเสนอ 5–8 จาก 20–30 ข้อ)

### G5. การบังคับ citation

ทางเลือก: (A) บังคับให้ทุกประโยคที่เป็นข้อเท็จจริงอ้าง chunk id แล้วตรวจด้วยโค้ดว่า id นั้นอยู่ในชุดที่ค้นได้จริง ตัดประโยคที่อ้างไม่ได้ · (B) อ้างระดับคำตอบรวมเท่านั้น
ผู้ร่างเสนอ: A (ตรวจด้วยโค้ดได้ ไม่ต้องใช้ LLM ตัดสิน) และแสดงชื่อเอกสาร ปี ฉบับ และหน้า; เอกสารไม่ระบุปีให้แสดง "ไม่ระบุปี"

### G6. Prompt injection จากข้อความในเอกสาร

ข้อความใน PDF ที่ถูกดึงเข้า prompt อาจมีคำสั่งแฝง (`L11 p18`) ชั้นป้องกันที่เสนอ: สแกน chunk หารูปแบบคำสั่ง · ครอบข้อมูลด้วยตัวคั่นและสั่งว่าเป็นข้อมูลไม่ใช่คำสั่ง · ใส่คำสั่งหลักซ้ำท้าย prompt (sandwich, `L11 p21`) · ให้ LLM ไม่มีเครื่องมือภายนอก (least privilege, `L13 p47`) · ตรวจผลลัพธ์ว่ามี citation ครบ
ต้องตัดสิน: ทำกี่ชั้นภายในเวลา (ผู้ร่างเสนอ 4 ชั้นหลักที่ไม่ต้องมีโมเดลเพิ่ม และข้ามการใช้ LLM ตรวจผลลัพธ์รอบสอง) และจะทำชุดโจมตีทดสอบกี่ข้อ (เสนอ 10–15)

### G7. ข้อความ "เพื่อการศึกษา"

ต้องตัดสิน: ตำแหน่งและความถี่ (แถบถาวรบน UI + ท้ายทุกคำตอบ?) และภาษา (ไทยอย่างเดียวหรือไทย+อังกฤษ) ผู้ร่างเสนอ: แถบถาวร + ท้ายคำตอบที่เกี่ยวกับการรักษา

## 3. Harness — ที่ต้องตัดสินใจ

### H1. รูปแบบ pipeline

| ทางเลือก | ลักษณะ | สไลด์ |
| --- | --- | --- |
| A. **Pipeline คงที่**: ถาม → guard → ค้น → (rerank) → ตอบ → ตรวจ citation | ทำซ้ำได้ วัดผลง่าย ไม่เปลือง token | `L12 p6` document pipeline |
| B. **Agent (ReAct)**: LLM เลือกเครื่องมือและวนค้นได้หลายรอบ | ตอบคำถามหลายขั้นดีกว่า | `L13 p8–11, p15` มีความเสี่ยงวนลูป/เรียกผิด |

ผู้ร่างเสนอ: **A เป็นหลัก** (ไม่ใช่ข้อบังคับของวิชา และคุมความปลอดภัยง่ายกว่า) ถ้าเหลือเวลาค่อยลอง B เป็น ablation · ต้องตัดสิน: ยอมรับหรือไม่

### H2. ใครเรียก LLM และตัวไหน

ต้องตัดสินร่วมกับทีม (เรื่อง API กำลังตัดสินกันอยู่): (A) API ภายนอก — ได้คุณภาพสูง แต่ทุกคำถามออกนอกเครื่อง (เกี่ยวกับ G1/G2) · (B) โมเดลเปิดรันเอง (Colab/เครื่อง) — ข้อมูลอยู่ในมือ แต่คุณภาพภาษาไทยและความเร็วเป็นข้อจำกัด
ผู้ร่างเสนอ: ส่วนค้นคืน (Track B) รันในเครื่องทั้งหมด; ส่วนตอบเลือกตามผลของทีม แต่ **ไม่ว่าเลือกแบบไหน input guard (G1) ต้องอยู่ก่อนเรียก LLM**

### H3. ชุดประเมินและเกณฑ์ผ่านของ guardrail

ชุดที่เสนอให้มี (ทั้งหมดต้องให้คนตรวจเป็น gold):
- gold/silver QA 20–30 ข้อ (มีแล้วในแผน Track B) · คำถามที่ "ไม่มีคำตอบ" 5–8 ข้อ · ชุดโจมตี prompt injection 10–15 ข้อ · ชุดข้อมูลส่วนบุคคลในคำถาม 8–10 ข้อ · ชุดคำถามข้ามกลุ่มประชากร (ผู้ใหญ่/เด็ก/ตั้งครรภ์/ผู้สูงอายุ) 6–8 ข้อ
- เมตริก: ค้นคืน (Recall@k, MRR; `L09`), คุณภาพคำตอบ (BERTScore `L14 p34–36`, RAGAS `L14 p52–53`) และ guardrail (อัตราปฏิเสธถูกต้อง/ปฏิเสธเกินจำเป็น/ปล่อยผ่านผิด)
- ถ้าใช้ LLM เป็นผู้ตัดสิน ต้องระวัง length bias และ position bias (`L14 p39–41`) สลับตำแหน่งตอบและให้คนสุ่มตรวจ

ต้องตัดสิน: ขนาดชุดแต่ละกลุ่ม, เกณฑ์ผ่าน (เช่น ปล่อยผ่านผิดต้อง 0 ในชุดโจมตี), และใครเป็นผู้ตรวจ gold

### H4. ขอบเขตงานของแต่ละ Track

ต้องตัดสิน: guard ส่วนไหนเป็นของใคร — ข้อเสนอ: B = ค้นคืน + เกณฑ์ตัดผลค้นไม่พอ + กรองประชากร + metadata ปี/ฉบับ · C = prompt, citation, abstain · D = UI, disclaimer, input guard, ชุดทดสอบ guardrail · A = ข้อมูล/PDPA ของ corpus

### H5. Harness สำหรับงานพัฒนา (Claude / Codex)

บทเรียนจากรอบตรวจ OCR: Claude คุม Codex แบบ supervisor ผลดีเมื่อบังคับรูปแบบผล + มีสคริปต์ตรวจ + คนอนุมัติ (`L13 p38, p46`)
ต้องตัดสิน: จะใช้รูปแบบเดียวกันต่อสำหรับงานอื่นหรือไม่ และ agent จะได้สิทธิ์เขียนอะไรได้บ้าง (ข้อเสนอ: เขียนได้เฉพาะโฟลเดอร์งานของตัวเอง ไม่ push, ไม่แตะ `.env`)
