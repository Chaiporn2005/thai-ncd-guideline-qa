# Strict และ lenient relevance (แก้ปัญหา "เฉลยหน้าเดียว")

เฉลยของแต่ละข้อคือหน้าเดียว แต่ข้อเท็จจริงเดียวกันอยู่ในหลายหน้า/หลายเล่มได้ (เช่น 70 มก./ดล. ของ q126) retriever ที่ดึงหน้าอื่นที่ตอบถูกจะถูกนับว่าพลาด
จึงรายงานสองค่าคู่กัน

| ค่า | นิยาม |
|---|---|
| **strict** (เดิม ไม่เปลี่ยน) | chunk เกี่ยวข้องเมื่อครอบคลุม `evidence` (edition + หน้า + quote อย่างน้อยครึ่งหนึ่ง) |
| **lenient** | strict **หรือ** ครอบคลุม `alt_evidence` **หรือ** (เฉพาะข้อที่มีหลักฐานข้อเดียวและคำตอบเป็นตัวเลข) chunk มีตัวเลข+หน่วยของคำตอบครบ และใช้คำที่หายากของคำถามร่วมกัน |

ข้อ `multi_page` ไม่ได้ lenient เพิ่ม (ต้องครบทุกหน้า) ช่องว่างระหว่าง strict กับ lenient คือจำนวนที่เฉลยหน้าเดียวบดบังไว้

## ส่วนประกอบ

1. **Schema** `question.schema.json`: เพิ่ม `alt_evidence[]` (ไม่บังคับ; `kind` = `duplicate` หรือ `same_fact`) ข้อ unanswerable ต้องว่าง
2. **หน้าซ้ำ** `scripts/build_alt_evidence.py`: หน้าอื่นที่มี quote ตรงตัว + ตัวเลขของคำตอบ **และทั้งหน้าเกือบเหมือนหน้าเฉลย** (Jaccard ของ 5-gram ≥ 0.7)
   ผลจริง: **1 จาก 143 ข้อ** (q001) เงื่อนไข "ทั้งหน้าเหมือน" จำเป็น เพราะลองแค่ quote ตรงตัวแล้วผิด: แถว "เกณฑ์เป้าหมาย ≥ร้อยละ 90" (q099) ซ้ำใต้ตัวชี้วัดคนละตัว และตารางผู้ตอบแบบสอบถามของ q098 พิมพ์ซ้ำหนึ่งครั้งต่อหัวข้ออบรมโดยตัวเลขเหมือนกัน
   ทั้งสองข้อ (q098, q099) จึงเป็น gold ที่กำกวมในตัวเอง ให้ผู้ตรวจพิจารณาปฏิเสธหรือเขียนให้ระบุหัวข้อ
3. **จับคู่ตามคำตอบ** `src/ncdqa/retrieval/answer_match.py`: ทำให้หน่วยเป็นรูปเดียว (มก./ดล. = มิลลิกรัม/เดซิลิตร = mg/dL, ร้อยละ 80 = 80%, เลขไทย, 1,350 = 1350)
   เลขที่ "แข็งแรง" คือ ≥ 2 หลัก ทศนิยม หรือมีหน่วย (ปี 25xx ไม่นับ) ต้องมีครบทุกตัวพร้อมหน่วยใกล้กัน และคะแนนคำซ้ำของคำถามที่ถ่วงด้วย idf (4-gram ที่หายากในคลังหน้า) ≥ **0.35**
   ปรับเทียบบนคำถาม 54 ข้อที่มีตัวเลข: หน้าเฉลยได้ค่ามัธยฐาน 0.27, หน้าอื่นที่มีแค่ตัวเลขเดียวกันได้ 0.06; ที่ 0.35 มีหน้าอื่นผ่านแค่ 7 จาก 2,879 (ตรวจดูแล้วเป็นข้อเท็จจริงเดียวกัน) ที่ 0.22–0.30 ราวครึ่งไม่เกี่ยว
   ค่า 0.35 จึงเป็น **ขอบล่าง** ที่ตั้งใจให้เข้ม
4. **ให้คะแนนใหม่โดยไม่เข้ารหัสซ้ำ** `scripts/rescore_runs.py`: อ่าน `results.jsonl` ของ run เดิม + chunk ที่ run ใช้ แล้วเขียน strict/lenient ลงโฟลเดอร์ใหม่ (`data/index/runs_rescored/`) สคริปต์หยุดถ้าค่า strict ไม่เท่าของเดิม
   `run_retrieval.py` ใหม่ (`--alt <sidecar>`) ออกทั้งสองค่าใน `metrics.json` (`overall` = strict, `lenient`)

## ผลบน dev silver (pilot ไม่ใช่ผลรายงาน)

12 run (bge-m3, e5-base × chunk 128/256/384/512 และ parent-child): ค่า strict ตรงกับเดิมทุก run

| ค่า min-overlap | R@5 เพิ่ม (strict → lenient) | หมายเหตุ |
|---|---|---|
| 0.35 (ค่าเริ่มต้น) | +0 ถึง +0.020 (0–2 ข้อต่อ run; ข้อที่ได้เพิ่มคือ q051 และ q054) | ขอบล่าง |
| 0.25 | bge t384 .680→.700, e5 t512 .640→.690, pc-bge .795→.815 | ปนข้อไม่เกี่ยวบ้าง |
| 0.15 | bge t384 .680→.730, e5 t512 .640→.730, pc-bge .795→.835 | ขอบบน มีข้อมูลที่ไม่เกี่ยวปน |

ผลคือ lenient **ไม่เปลี่ยนอันดับ** ของ variant ในระดับที่เชื่อได้ ช่องว่างที่เห็นจริงอยู่ที่ 0–2 จุด ที่ขอบล่าง และอย่างมาก 5–9 จุดที่ขอบบนที่ปนข้อมูลไม่เกี่ยว
จึงรายงานเป็น "ช่วง" และไม่ใช้ lenient แทน strict

## ข้อจำกัด

- ครอบคลุมเฉพาะคำตอบที่เป็นตัวเลข (ราว 1/3 ของข้อ); ข้อ fact/condition ที่ไม่มีตัวเลขต้องอาศัย `alt_evidence` ที่คนยืนยัน (`kind: same_fact`) ซึ่งยังไม่มี
  ตัวช่วย: `scripts/find_alt_evidence.py` เสนอรายการหน้า (53 จาก 169 ข้อ) ให้คนอ่านแล้วเติม
- idf คำนวณจากคลังหน้า v11 และปรับเทียบบนชุด silver ชุดเดียวกับที่ใช้ทดสอบ ควรตรวจซ้ำเมื่อ corpus เปลี่ยน
- test ต้องใช้กติกาเดียวกันตั้งแต่ก่อนรัน (ห้ามเลือกกติกาหลังเห็นผล)
