# Data engineering rules

กติกาสำหรับทุกคนและทุก agent ที่ทำงานกับ `data/` ตั้งแต่ดาวน์โหลดจนถึง chunks
อ่านคู่กับ [corpus policy](corpus_policy.md) และ [review ล่าสุด](reviews/20261006-data-engineering-review.md)

- สถานะ: ข้อเสนอจาก review 2026-10-06 รอ coordinator รับเป็น decision (ดู proposal 0006)
- ตัวเลขเกณฑ์ในเอกสารนี้เป็น **ค่าตั้งต้น** ต้องปรับด้วยผลจาก pilot แล้วบันทึกเป็น decision
- อ้างสไลด์รายวิชาแบบ `L<lecture> p<หน้า>` เช่น `L14 p21` = NLP-DL-14 หน้า 21

## 1. หลักการ (ใช้ตัดสินกรณีที่กติกาไม่ได้เขียนไว้)

| # | หลักการ | เหตุผล |
| --- | --- | --- |
| P1 | **Raw ห้ามแก้** ทุกขั้นอ่าน input แล้วเขียน output ใหม่ | ย้อนตรวจและสร้างใหม่ได้เสมอ |
| P2 | **ทุกขั้นสร้างซ้ำได้** จากโค้ด commit + config + input hash | ผลทดลองต้อง reproduce ได้บน clean clone |
| P3 | **Writer เดียวต่อพื้นที่** | กันไฟล์ชนกันระหว่างคนและ agent |
| P4 | **ทุก chunk ตรวจย้อนถึงหน้า PDF ได้** | คำตอบทางคลินิกต้องอ้างหลักฐานได้ |
| P5 | **ไม่เดาตัวเลข หน่วย เงื่อนไข และคำปฏิเสธ** ถ้าไม่แน่ใจให้ติดธงส่งคนตรวจ | ความผิดพลาดตรงนี้เป็นอันตรายและตรวจจับยากที่สุด |
| P6 | **ถูกก่อนแล้วค่อยแพง** ใช้ตัวตรวจราคาถูกก่อน แล้วค่อยใช้ OCR หรือคน กับส่วนที่เหลือ | สไลด์ L14 p10, p30: เรียงขั้นตามต้นทุนและอัตราที่คัดออก |
| P7 | **วัดก่อนเลือก** ทุกเทคนิคต้องเทียบกับทางเลือกอย่างน้อย 1 ทางบนข้อมูลของเรา | ตามกติกาการตัดสินใจ (ส่วนที่ 4) |

## 2. ข้อมูลอยู่ที่ไหน

| ชั้น | ที่เก็บ | Writer | ขึ้น Git |
| --- | --- | --- | --- |
| Manifest, schema, รายงาน, `retrieval.json`, `extraction.json` | `data/` ใน repo | curator / owner สาย | ขึ้น (ตาม allowlist) |
| Raw PDF | `data/raw/<document_id>/source.pdf` + สำเนาที่ช่องทางแชร์ของทีม (Google Drive แบบ private เฉพาะสมาชิก) | curator | ไม่ขึ้น |
| ข้อความรายหน้า (raw + normalized) | `data/processed/<corpus_version>/...` + Drive | curator | ไม่ขึ้น (ขึ้นแค่ summary) |
| Chunks | `data/processed/<corpus_version>/chunks/<chunk_config_id>/` + Drive | owner สาย RAG | ไม่ขึ้น |
| Embeddings / index | `data/indexes/<corpus_version>/` เครื่องใครเครื่องมัน | สร้างเอง | ไม่ขึ้น |

- `corpus_version` บน Drive **ห้ามแก้ทับ** ถ้าแก้ให้ออก version ใหม่ (`v0.1-pilot`, `v0.2`, `v1.0-frozen`)
- ทุก version มีไฟล์ hash ของทุกไฟล์ ไฟล์นี้ขึ้น Git เพื่อให้ทุกเครื่องตรวจก่อนใช้
- Path ของแต่ละเครื่องอยู่ใน config ที่ถูก ignore ห้ามฝัง path เครื่องหรือ path runtime ของ agent ใน docs/โค้ด
- ตัวเลือกภายนอก: [DVC](https://dvc.org/) ใช้ Google Drive เป็น remote ได้ และผูก hash กับ Git ให้อัตโนมัติ
  ถ้าจะใช้ต้องบันทึกเป็น decision ก่อน

## 3. Pipeline และกติกาแต่ละขั้น

ลำดับขั้นอิงสไลด์ L12 p6 (Load → Parse → Chunk → Embed → Index) และ L14 p3
(Source → Filter → Deduplicate → Evaluate → Audit)

### S1 Source — รับไฟล์

- ทุกไฟล์มี `retrieval.json`: URL ที่ใช้จริง, วันที่, hash, ขนาด, จำนวนหน้า, ช่องทาง
- แหล่งที่ติด 403: ให้**คน**ดาวน์โหลดผ่านเบราว์เซอร์จากหน้าของผู้จัดทำ แล้วบันทึกช่องทางเป็น
  `team_manual_download` ห้ามใช้สคริปต์หลบการบล็อก ปลอม user-agent หรือใช้บัญชีคนอื่น
- ตรวจปก/ชื่อ/ปี/ผู้จัดทำตรงกับ manifest ก่อนเข้าขั้นถัดไป

### S2 Rights — สิทธิใช้งาน

- ทีมตัดสินใช้เอกสารเพื่อการศึกษาในรายวิชา (ดู proposal 0006) โดยมีเงื่อนไข:
  repo และ Drive เป็น private, ไม่เผยแพร่ไฟล์หรือข้อความเต็มต่อ, ไม่ deploy เป็นบริการสาธารณะ, อ้างแหล่งทุกครั้ง
- การตัดสินนี้เป็นการตัดสินของทีม ไม่ใช่การอนุญาตจากผู้จัดทำ แหล่งที่ประกาศชัดว่าต้องขออนุญาตก่อน
  (สื่อศูนย์เบาหวานศิริราช 9 รายการ) ให้บันทึกแยกว่าใช้ภายใต้เงื่อนไขใด และควรส่งคำขออนุญาตควบคู่
- เก็บหลักฐานสิทธิไว้ใน rights queue เหมือนเดิม ห้ามลบ notice ลิขสิทธิ์ออกจากต้นฉบับ

### S3 Parse — สกัดข้อความรายหน้า

- เก็บผลรายหน้า เลขหน้า PDF แบบ 1-based ทุกหน้ารวมหน้าว่าง
- **สถานะรายหน้า** (แทนสถานะรายเล่ม):

  | สถานะ | ความหมาย | ขั้นต่อไป |
  | --- | --- | --- |
  | `text_ok` | ผ่านตัวตรวจทั้งหมด | S4 |
  | `text_pua` | มีอักขระ Private Use Area | ลอง mapping ใน S4 ก่อน OCR |
  | `text_garbled` | อักขระผิดแบบที่ mapping แก้ไม่ได้ | S5 OCR |
  | `image_only` | ไม่มี text layer แต่มีภาพ | S5 OCR |
  | `blank` | ไม่มีทั้งข้อความและภาพ | ข้าม แต่เก็บเลขหน้า |
  | `table_or_figure` | มีตาราง/flowchart ที่มีข้อมูลทางคลินิก | S6 คนตรวจทุกหน้า |

- เทียบตัวสกัดอย่างน้อย 2 ตัวบน pilot เช่น pypdf กับ PyMuPDF หรือ pdfminer.six (L12 p8 ระบุ PyMuPDF/pdfminer.six/unstructured)
  แล้วเลือกจากผลวัด เพราะ PDF ไทยแต่ละเล่มใช้ font ต่างกันและตัวสกัดแต่ละตัวจัดการ ToUnicode map ต่างกัน
- ตัวตรวจคุณภาพรายหน้า (ราคาถูก รันก่อน ตามหลัก P6):
  - สัดส่วนอักขระไทยมาตรฐานต่ออักขระทั้งหมด
  - จำนวนอักขระ PUA, replacement (U+FFFD) และ control
  - สถิติแบบ Gopher (L14 p11) ปรับสำหรับภาษาไทย: ตัดคำก่อน (เช่น PyThaiNLP) แล้วดูความยาวคำเฉลี่ยและสัดส่วนคำที่อยู่ในพจนานุกรม
    ข้อความที่ font map เสียมักได้ "คำ" ที่ไม่มีในพจนานุกรมจำนวนมาก
  - ภาษาด้วย fastText `lid.176` (L14 p7) เป็นสัญญาณเสริม ระวังว่าข้อความสั้นจะไม่แม่น
- **ข้อควรระวังจาก L14 p12–13:** กฎกรองแบบ C4/Gopher ตัดตารางที่มีตัวเลขเยอะทิ้ง
  ในงานนี้ห้ามใช้ตัวตรวจเหล่านี้**ลบ**หน้า ให้ใช้แค่**ติดธง**แล้วส่งไปขั้นที่เหมาะ
  เพราะตารางค่าเป้าหมายและขนาดยาคือข้อมูลสำคัญที่สุด

### S4 Normalize — ทำข้อความให้เป็นมาตรฐาน

- เก็บ `text_raw` และ `text_norm` คู่กันเสมอ
- กฎที่ทำได้ (ทุกกฎต้องมี unit test จากตัวอย่างจริง):
  - Unicode NFC
  - Map อักขระ PUA ที่รู้ความหมายกลับเป็นอักขระไทยมาตรฐาน ด้วยตาราง mapping ใน Git
    (สมมติฐานที่ต้องพิสูจน์: PDF ไทยรุ่นเก่ามักใช้ glyph ช่วง U+F700–U+F71A แทนสระ/วรรณยุกต์ที่ยกระดับ)
  - ลบ zero-width space, soft hyphen, control characters
  - ลบ running header/footer: บรรทัดที่ซ้ำในหน้าส่วนใหญ่ของเล่มเดียวกัน
    (เหตุผลจาก L12 p11: ข้อความซ้ำทุกหน้าทำให้ chunk แบบเดียวกันโผล่ใน top-k ของทุกคำถาม หรือ hubness)
- **ห้าม:** แก้ตัวเลข หน่วย (mg/dL, mmHg, mmol/L, mL/min/1.73 m²), เครื่องหมาย ≥ ≤ < > ±, คำปฏิเสธ,
  และลำดับเงื่อนไขในตาราง ถ้ากฎไหนแตะสิ่งเหล่านี้ให้ติดธงแทน
- วัดผล normalize: จำนวนหน้าที่เปลี่ยนจาก `text_pua` เป็น `text_ok` และผลสุ่มตรวจด้วยคน

### S5 OCR — เฉพาะหน้าที่ต้องใช้

- OCR เฉพาะ `image_only` และ `text_garbled` ไม่ OCR ทั้งเล่มถ้าไม่จำเป็น (P6)
- เทียบอย่างน้อย 2 วิธีบนหน้าชุดเดียวกัน ตัวเลือกภายนอกที่ทดสอบได้ เช่น Tesseract `tha`,
  EasyOCR, หรือโมเดล OCR เอกสารภาษาไทย (เช่น Typhoon OCR)
- วัดด้วย **CER ระดับอักขระ** กับข้อความที่คนพิมพ์เทียบ (เช่น ใช้ `jiwer`)
  ใช้ CER ไม่ใช่ WER เพราะภาษาไทยไม่มีขอบเขตคำที่แน่นอน (เหตุผลเดียวกับที่ L14 p9 ใช้ token ต่ออักขระแทน fertility)
- บันทึกเครื่องมือ, version, ภาษา, DPI, ค่า config ทุกครั้ง
- หน้าที่มีตัวเลขทางคลินิก: คนตรวจทุกตัวเลข ไม่ว่า CER จะต่ำแค่ไหน
- OCR ผ่าน API หรือบริการภายนอก = ส่งเนื้อหาออกนอกเครื่อง ต้องมี decision เรื่องงบและสิทธิก่อน

### S6 Review — คนตรวจ

- แต่ละเอกสารตรวจอย่างน้อย 3 หน้า (ต้น กลาง ท้าย) + ทุกหน้า `table_or_figure`
- Review record: `document_id`, หน้า, ผู้ตรวจ, วันที่, ประเภทข้อผิดพลาด, ตัวอย่าง, ผล (`pass`/`fix`/`reject`)
- ผู้ตรวจไม่ใช่คนที่สกัดเอกสารนั้น
- ห้ามเลื่อนสถานะเพื่อให้ถึงยอด

### S7 Deduplicate — ตัดเนื้อหาซ้ำ

- **Exact:** SHA-256 ของไฟล์ และของ `text_norm` (L14 p21)
- **Near-duplicate:** shingles + Jaccard (L14 p22) แล้วให้คนตัดสินคู่ที่เกินเกณฑ์
  - ภาษาไทยไม่มีเว้นวรรคระหว่างคำ ให้ใช้ character k-gram หรือตัดคำก่อนทำ shingle
  - corpus นี้มีแค่หลักสิบเอกสาร เทียบ Jaccard ตรงทุกคู่ได้เลย ไม่ต้องใช้ MinHash/LSH
    (L14 p28: MinHash/LSH มีไว้ลดจำนวนคู่ในระดับพันล้านเอกสาร) ถ้าจะใช้ต้องมีเหตุผลอื่น
  - ผลที่ได้เป็นแค่ candidate ไม่ใช่หลักฐานว่าซ้ำ (L14 p29) คนต้องตรวจความสัมพันธ์ฉบับ
- ฉบับต่างปีของงานเดียวกันไม่ใช่ duplicate เก็บทั้งคู่และบันทึกความสัมพันธ์ฉบับ

### S8 Accept และ freeze

- Curator (คนที่มีชื่อ) ตั้ง `accepted` เมื่อผ่าน S1–S7 พร้อมหลักฐาน
- Freeze เป็น `corpus_version` พร้อมไฟล์ hash
- รายงาน **funnel** ทุก version (L14 p6): จำนวนที่เหลือแต่ละขั้นและเหตุผลที่ตกหล่น เช่น
  `selected → local PDF → extracted → normalized/OCR → reviewed → accepted`
- รายงานแยก: works, editions, pages, chunks ห้ามนับหน้าหรือ chunk เป็นเอกสาร

### S9 Chunk — contract กับทีม RAG

- นับ token ด้วย tokenizer ของ embedding model ที่ใช้จริง (L12 p10)
  และ chunk ต้องไม่ยาวเกิน max sequence length ของโมเดล เพราะส่วนเกินถูกตัดทิ้งเงียบๆ
- แบ่งตามโครงสร้างก่อน: บท > หัวข้อ > ย่อหน้า > ประโยค > token (L12 p8) ไม่ใช้ fixed-size อย่างเดียว
  เพราะจะตัดกลางตารางและเอาเนื้อหาคนละหัวข้อมารวมกัน (L12 p7)
- ตาราง: ห้ามตัดกลาง ถ้าเกิน limit ให้แยกเป็นกลุ่มแถวพร้อมซ้ำหัวตาราง (L12 p8)
- ทางเลือกที่ทดลองได้: semantic breakpoint chunking ด้วย embedding (L12 p9)
- ทุก chunk เก็บ: `chunk_id`, `document_id`, `edition_id`, `pdf_page_start`, `pdf_page_end`,
  `printed_page` (ถ้ารู้), `section_path`, `text`, `token_count`, `chunk_config_id`, `corpus_version`
- ขนาด chunk และ overlap ตัดสินจากการทดลองอย่างน้อย 2 ค่า (ทีม RAG เป็น owner)
- รายงาน: จำนวน chunk ที่ถูก truncate ต้องเป็น 0 และการกระจายของ token ต่อ chunk

## 4. กติกาการตัดสินใจ (decision record)

ทุกการเลือกวิธีในเอกสารนี้ต้องมี decision record ที่**มีหลักการ มีเหตุผล มีที่มา และทุกคนอธิบายได้**
ใช้เทคนิคนอกสไลด์ได้ ถ้าอ้างแหล่งที่ตรวจได้ อธิบายกลไกด้วยคำของตัวเองได้ และเทียบกับวิธีพื้นฐาน

บันทึกใน `NCD - 1Orchestra/decisions/` ตามรูปแบบเดิมของ repo และเพิ่มช่องเหล่านี้:

```markdown
- ขั้น: <S1–S9>
- ปัญหาและหลักฐาน: <อะไร เกิดจริงที่ไหน ตัวเลขเท่าไร>
- ตัวเลือก (≥2): <A> / <B> / <ไม่ทำ>
- หลักการและที่มา: <แนวคิด> — <L<n> p<n> | paper/เอกสาร + ลิงก์>
- ผลวัด: <ตัวเลข + คำสั่ง reproduce> หรือ "ยังไม่มี จะวัดโดย …"
- ผลตัดสิน: <เลือกอะไร>
- Owner: [Human] | [AI-suggested, Human-approved] | [AI-decided] — <ชื่อคน>
- ถ้าผิดจะเห็นอะไร: <อาการ>
- ทบทวนเมื่อ: <เงื่อนไข>
```

กฎ:

1. เหตุผลต้องโยงกับข้อมูลของเรา "เป็นวิธีที่นิยม" หรือ "AI แนะนำ" ไม่นับเป็นเหตุผล
2. ข้อเสนอจาก agent ต้องมีคนตรวจและติด owner `[AI-suggested, Human-approved]`
3. ไม่มีผลวัดให้เขียนว่าไม่มี ห้ามแต่งตัวเลขหรือแหล่งอ้างอิง
4. เปลี่ยนใจได้ด้วย decision ใหม่ที่อ้างฉบับเก่า ห้ามแก้ฉบับเก่าทิ้ง
5. decision เหล่านี้คือวัตถุดิบของ Decision Journal ใน `AI_AUDIT.md` และเมื่อ agent ทำผิดทางเทคนิค
   ให้จดลง Error Catch ทันที

## 5. Checklist ก่อนส่งงาน data แต่ละรอบ

- [ ] รันบน clean clone ได้ด้วยคำสั่งที่เขียนไว้ ไม่มี path เฉพาะเครื่อง
- [ ] Output มี hash และ `corpus_version`
- [ ] สถานะรายหน้าครบทุกหน้า
