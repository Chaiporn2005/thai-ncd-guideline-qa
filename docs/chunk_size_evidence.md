# หลักฐานเรื่องขนาด chunk (ให้ตัดสินใจ — ยังไม่ได้เลือก)

เตรียมโดย Claude เมื่อ 2026-10-10 จากการค้นเว็บ; ตัวเลขในตารางคัดจากตารางในเปเปอร์ (v2) แต่ **ยังไม่ได้รันซ้ำและไม่ได้อ่านเปเปอร์ทั้งเล่ม**
ผู้ตัดสินใจ: เจ้าของ Track B. สถานะ: ข้อมูลประกอบการตัดสินใจ ไม่ใช่ข้อสรุป

## 1. สิ่งที่งานวิจัยบอก

### 1.1 Bhat et al. 2025, "Rethinking Chunk Size For Long-Document Retrieval" ([arXiv 2505.21700](https://arxiv.org/abs/2505.21700))

ทดสอบ fixed-size chunk 64–1024 token กับ embedding 2 ตัว (Stella, Snowflake) บน 6 ชุดข้อมูล วัด Recall@1

| ชุดข้อมูล (token/เอกสาร) | โมเดล | 64 | 128 | 256 | 512 | 1024 |
|---|---|---|---|---|---|---|
| NarrativeQA (51,830) | Stella | .042 | .057 | .079 | .089 | **.107** |
| NQ (6,918) | Stella | .172 | .222 | .323 | **.385** | .349 |
| NQ | Snowflake | .150 | .204 | .263 | .390 | **.477** |
| NewsQA* (8,485) | Stella | .378 | .440 | .491 | **.560** | .520 |
| COVID-QA* (10,009) | Stella | **.521** | .418 | .424 | .406 | .308 |
| COVID-QA* | Snowflake | .390 | **.532** | .409 | .432 | .542 |
| TechQA* (7,597) | Stella | .049 | .165 | .400 | .614 | **.619** |
| SQuAD* (7,998) | Stella | **.642** | .616 | .566 | .498 | .386 |

\* เอกสารสังเคราะห์ที่ต่อชุด QA สั้นๆ เข้าด้วยกัน. แถว Snowflake ของ NarrativeQA/NewsQA/TechQA/SQuAD ในเปเปอร์ไม่แสดงที่นี่เพื่อความกระชับ (ดูเปเปอร์)

ข้อสรุปของผู้เขียน: คำถามสั้นแบบข้อเท็จจริงเหมาะกับ chunk เล็ก (64–128) ส่วนคำถามที่ต้องบริบทกว้างเหมาะกับ chunk ใหญ่ (512–1024) และโมเดล embedding ต่างกันไวต่อขนาดต่างกัน
**ข้อควรระวัง:** ข้อความในเปเปอร์ขัดกับตารางเล็กน้อยบางจุด (เช่น NQ peak, ตัวเลข TechQA ของ Snowflake ที่ 64) จึงควรใช้ตัวเลขในตารางเป็นหลัก

### 1.2 "Searching for Best Practices in RAG" ([arXiv 2407.01219](https://arxiv.org/abs/2407.01219))

เทียบขนาดหน่วย 128–2048 token บนคลังเอกสาร 60 หน้า วัด faithfulness/relevancy (ไม่ใช่ recall): 256 และ 512 token ให้ผลดีที่สุดทั้งสองค่า ส่วน 2048 แย่ที่สุดด้าน faithfulness. คลังเล็กและไม่ใช่ภาษาไทย/คลินิก

### 1.3 งานคลินิก: "Comparative Evaluation of Advanced Chunking for RAG ... Clinical Decision Support" ([Bioengineering 2025/2026, PMC12649634](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12649634/))

เทียบ chunking 4 แบบ (adaptive ตามความยาว, proposition, semantic, fixed token) บนคำถาม 30 ข้อเรื่องหลังศัลยกรรมจมูก (Gemini 1.0 Pro): adaptive ได้ accuracy 87% เทียบ fixed 50% (p = 0.001); precision 0.50 / recall 0.88 เทียบ 0.17 / 0.40.
**ข้อจำกัดหนัก:** สาขาเดียว คำถาม 30 ข้อ โมเดลเดียว ผู้ตัดสินเป็นคน; บล็อกบางแห่งอ้างว่า 13% vs 50% ซึ่งขัดกับบทคัดย่อ จึงไม่ใช้บล็อกเหล่านั้น. ใช้ได้แค่เป็นสัญญาณว่า chunk ที่ตัดตามโครงสร้างน่าจะดีกว่าตัดตามความยาวล้วนๆ

## 2. การนำไปใช้กับคลังของเรา

| ประเด็น | ผลต่อการเลือก |
|---|---|
| คำถามของเราส่วนมากเป็นข้อเท็จจริง/ตัวเลข/เกณฑ์ (ค่าเป้าหมาย ขนาดยา) → คล้าย SQuAD/COVID-QA ที่ chunk เล็กชนะ | เอนไปทาง 128–256 |
| แต่คำตอบหลายข้ออยู่ในตาราง/เงื่อนไขที่ต้องมีบริบทรอบ (เช่นเกณฑ์ตามกลุ่มผู้ป่วย) → คล้าย TechQA/NQ ที่ chunk ใหญ่ชนะ | เอนไปทาง 512 |
| เราตัดตามโครงสร้าง (บรรทัด/ตาราง/บท) ไม่ใช่ fixed จึงไม่ตรงกับเงื่อนไขของเปเปอร์ที่ 1 | ตัวเลขเป็นแนวทาง ไม่ใช่คำทำนาย |
| e5-base รับ ≤ 512 token; bge-m3 รับได้ถึง 8,192 แต่ตอนนี้จำกัด 512 เพื่อเทียบกันได้ | 1024 ใช้กับ e5 ไม่ได้ |
| เปเปอร์เห็นว่าโมเดลต่างกันตอบสนองต่อขนาดต่างกัน | ต้องทดสอบ **ทั้งสองโมเดล** ที่ทุกขนาด |

## 3. ข้อเสนอการทดลอง (รอตัดสินใจ)

เปรียบเทียบ chunk 128 / 256 / 512 token × โมเดล e5-base, bge-m3 วัด Recall@5/10 และ MRR บน dev set (ต้องมี gold ก่อนจึงจะตัดสินผล). ตอนนี้มี chunk 256 และ 512 แล้ว; 128 สร้างเพิ่มได้ในไม่กี่นาที. เพิ่ม 1024 เฉพาะ bge-m3 ได้ ถ้าอยากทดสอบว่าบริบทยาวช่วยตาราง
คำถามที่ต้องตัดสิน: (ก) จะรวม 128 หรือไม่ (ข) จะทดสอบ 1024 กับ bge-m3 หรือไม่ (ค) จะเลือก chunk size ที่ใช้ต่อ ด้วยเกณฑ์ใด (Recall@5 อย่างเดียว หรือรวม latency/ขนาดดัชนี)
