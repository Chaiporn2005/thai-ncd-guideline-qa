## 1. ตัวอย่างที่ถาม: "ผู้ป่วยโรคไตเรื้อรังระยะ 3 ควรใช้ยา metformin ขนาดเท่าไร"
- **คำตอบก่อนแก้ ไม่ผิดแต่ไม่ครบ (ประมาณ partial):** บอกว่า eGFR 45–59 "อาจพิจารณาปรับขนาด" และ metformin แนะนำเมื่อ eGFR ≥ 30 ทั้งสองข้อมีใน ckd-guideline-2565 ข้อ 7.4.1 แต่**หายข้อสำคัญที่สุด** คือ "ปรับลดขนาดยาเมื่อ eGFR < 45" และไม่มีขนาดยาเป็น มก. (ข้อความที่ค้นมาไม่ระบุตัวเลข มก.; ถ้ามีอยู่ในรูปที่ 7.7 ระบบไม่เห็น)
- **สาเหตุที่ข้อสำคัญหาย: validator ของเราตัดเอง** โมเดลเขียน claim "ผู้ป่วยโรคไตเรื้อรังระยะ 3 ควรปรับลดขนาดยา metformin เมื่อ eGFR ต่ำกว่า 45" อ้าง S3 ถูกต้อง แต่กฎ "ตัวเลขใน claim ต้องอยู่ในหลักฐานที่อ้าง" เจอเลข **3** (ที่ผู้ใช้เขียนเองในคำถาม "ระยะ 3") ซึ่งไม่อยู่ในหลักฐาน จึงตัดทิ้ง
- **แก้แล้ว (demo เท่านั้น):** validator โปรไฟล์ **N8** = N7 + อนุญาตเลขที่ผู้ใช้เขียนเองในคำถาม รันซ้ำจาก cache: claim นั้นกลับมา คำตอบมีครบทั้ง "<45 ลดขนาด", "45–59 พิจารณา", "≥30 ใช้ได้" ยังไม่มี มก. เพราะหลักฐานไม่มี
- **คำถามว่า "ระยะนี้" (ไม่บอกโรค/ระยะ):** โมเดลงดตอบถูกต้อง (ไม่มีบริบทพอ) เป็นพฤติกรรมที่ต้องการ ไม่ใช่ข้อบกพร่อง

## 3. สาเหตุเชิงกลไกทีละข้อ
- **R4 validator ตัดเกิน (ตรวจเจอจากเคส metformin แล้วนับต่อ):** จากคำตอบที่ถูกตัด 13 claim ใน dev+test (ทั้งหมดเป็นกฎเลข) มี **6 claim ที่เลขที่ถูกตัดคือเลขที่ผู้ใช้เขียนเองในคำถาม** (ปี 2568, 2565, 100 กรัม, ระยะ 3) ผลของโปรไฟล์ N8 ต่อคะแนน dev: correctness A 0.856→0.861, B 0.876→0.871, C 0.902→0.907 (อยู่ในความแปรปรวนของ judge ±0.01); จำนวนคำตอบที่เปลี่ยน 2–3 ข้อต่อระบบ จึง**ไม่มีประโยชน์ที่วัดได้ในภาพรวม** แต่มีประโยชน์ชัดต่อเคสที่ claim สำคัญหายอย่าง metformin ตัดสินใจ: ใช้ N8 ใน demo, **ตัวเลข frozen_v1 และ frozen_react_v1 ยังเป็น N7 ไม่แก้ย้อนหลัง** (การเปลี่ยนจริงต้อง freeze ใหม่และรัน test ครั้งเดียว)
  - ทำไมไม่ขยายไปถึง "คำอังกฤษจากคำถาม" (เช่น HbA1c ใน q004 ที่ทำให้ได้คำตอบว่าง): กฎคำอังกฤษเป็นด่านที่ช่วยกัน injection (ASR adaptive 0.43→0.14 ตามรายงานข้อ 6) ถ้ายอมคำอังกฤษจากคำถามจะเปิดช่อง canary จึงคงตัดไว้ และบันทึก q004 เป็นต้นทุนที่ยอมรับ
- **R1 ค้นพลาด:** เกิดกับคำถามเชิงตัวเลขเฉพาะที่ถ้อยคำในเอกสารต่างจากคำถามมาก (q155 "ประมาณ 7 ล้านคน" มีหลายแหล่งที่ให้ 7.6–8 ล้านคน) ค้นเจอหน้าใกล้เคียงแต่ไม่ใช่หน้าเฉลย
- **R3 ตาราง:** chunk ของตารางถูกแตกเป็นแถวและหัวคอลัมน์อยู่คนละที่ (เลขกับหน่วย/ชนิดอาหารแยกกัน) โมเดลจึงสลับเลข (dev q040 ตอบ 18 และ 8 แทน 468 และ 98) ReAct ทำได้ดีกว่าเล็กน้อยที่ table (0.71 เทียบ 0.64) เพราะค้นซ้ำได้ แต่ n=7
- **R5 / q163:** โมเดลเติมประโยคปฏิเสธที่ขัดกับ claim ก่อนหน้า validator ตรวจแค่ citation/ตัวเลข ไม่ตรวจความสอดคล้องระหว่าง claim
- **ตอบทั้งที่ไม่ควร (ชุดไม่มีคำตอบ n=4):** q157 หญิงตั้งครรภ์ที่เป็นไตระยะ 4 → A/B/D ตอบเพดานโซเดียมของผู้ป่วยไตทั่วไป (ประชากรใกล้เคียงแต่ไม่ตรง) q146 → D และ ReAct ตอบ ระบบไม่มีตัวตรวจ "ประชากรไม่ตรง"
- **ReAct เสียเฉพาะตัว:** ค้นเองแล้ว query drift (dev hit@5 0.78–0.85 ก่อนใช้ seed search), ต้นทุน 5.5 เท่า, งดตอบถูกกับข้อไม่มีคำตอบน้อยกว่า (OWASP: 2/5 เทียบ 4/5), `parse_error` 3–4 ข้อ, condition ต่ำกว่า B (0.72 เทียบ 0.94)

## 4. ข้อควรสงสัยของตัววัด (ไม่ใช่ข้อผิดพลาดของระบบ)
- **faithfulness ที่ judge เห็นแต่ claim:** claim ที่ฝากบริบทไว้กับคำถาม ("อย่างน้อย 14 ค่า" โดยไม่พูดว่า "วัดต่อเนื่อง 4–6 ชั่วโมง") ถูกให้ unsupported ทั้งที่ chunk ที่อ้างมีข้อความนั้นตรงตัว ใน B มี 6 ข้อที่ correctness=correct, citation ถูก แต่ faithfulness ≤ 0.33 การทดสอบเล็ก (12 ข้อ): ถ้าให้ judge เห็นคำถาม q031, q147, q152 เปลี่ยน 0 → 1; ข้อที่ตอบผิดจริงที่ใช้เป็นตัวควบคุม (q155, q163) ไม่เปลี่ยน; q175 ลดลง (1.0 → 0.67) ผลเต็มของ test ใน §5
- **judge ไม่นิ่ง:** q175 faithfulness ครั้งแรก 0.33 ครั้งถัดมา 1.0 ด้วย prompt เดียวกัน ความแปรปรวนต่อข้อสูง ใช้ดูค่าเฉลี่ยระดับกลุ่ม ไม่ใช้ตัดสินรายข้อ
- **hit@5 เข้มกว่าความจริง:** นับเฉพาะหน้าที่เฉลยระบุ ข้อ q003 ตอบถูกจากหน้าอื่น
- **BERTScore แทบไม่ไวต่อถูก/ผิด** (F1 ต่างกันราว 0.018) ใช้ดูอย่างเดียว ไม่ใช้ตัดสิน

## 6. ฝั่ง guardrail (silver)
- **ผ่านเกณฑ์ "ถึงผู้ใช้ = 0"**: pipeline คงที่ 0/45 (ดิบจากโมเดล 6/45 ที่ถูก validator/output guard กั้น), ReAct 1/51 (O-DSE ผู้ใช้สั่งเอง ไม่ใช่ช่องโหว่)
- **ข้อบกพร่องของเคสที่จับได้เองและแก้แล้ว:** LLM08 รุ่นแรกใช้ข้อความปลอมไม่ตรงหัวข้อ, ตัวตัดสินด้วยวลีนับประโยคปฏิเสธเป็นสำเร็จ, เกณฑ์ RESOURCE ปรับหลังเห็นผล (บันทึกใน `docs/owasp_guardrails.md` §5)
- **ยังกันไม่ได้โดยโครงสร้าง:** chunk ปลอมที่เขียนเหมือนแนวทางจริง (LLM08), ชื่อบุคคลที่ไม่มีคำนำหน้า (mask พลาด), กฎขอบเขตที่เป็น pattern ("ผู้ป่วยระยะนี้" ที่ไม่มีสรรพนามบุคคลผ่านกฎ)
- **คำถามปกติถูกปฏิเสธเกิน:** 1/20 (pipeline), 2/20 (ReAct)

ตามกติกา (correctness ≥ v1 − 0.01, faithfulness ≥ v1 − 0.02, ปฏิเสธผิดไม่เกิน v1 + 2, งดตอบถูกไม่ลดลง และมีสิ่งที่ดีขึ้นอย่างน้อยหนึ่งอย่าง ทั้ง B และ C): **B ไม่ผ่าน** (faithfulness ลด 0.051), **C ไม่ผ่าน** (correctness ลด 0.031) → **ไม่ใช้ v2 และไม่รัน test** ความต่างที่เห็น (B +0.026, C −0.031) อยู่ในระดับความแปรปรวนของ judge ±0.03 จึงสรุปได้เพียงว่า **ไม่พบประโยชน์ที่แยกจากสัญญาณรบกวน** และ faithfulness ของ B ลดลงจริง (คาดว่ากฎ "ตอบครบ/4 claim" ทำให้มี claim เพิ่มที่รองรับไม่ครบ)
- การงดตอบถูกกับข้อไม่มีคำตอบไม่ดีขึ้นบน dev (8/9 และ 7/9 เท่าเดิม) กลุ่มประชากรที่ต้องการแก้ (q157) อยู่ใน test ซึ่งเราไม่แตะ จึงยังไม่มีหลักฐานว่าตัวตรวจกลุ่มประชากรได้ผล
- ข้อผิดพลาดของผมระหว่างทำ: รอบแรกที่ตัดสิน dev v2 เริ่มตอนการสร้างคำตอบยังไม่จบ (เห็นแค่ 36 จาก 106 ข้อ) ผลนั้นใช้ไม่ได้ ทิ้งแล้วรันใหม่ตอนไฟล์ครบ
- ที่เก็บไว้ในโค้ด (ค่าเริ่มต้นปิด): ตัวเลือก validator `validator_reattribute`, `validator_drop_denials`, `validator_population` และ prompt p4 ใช้ทำการทดลองต่อได้ ไม่มีตัวใดอยู่ใน demo ยกเว้น N8 (เลขจากคำถาม)

ตามกติกา: **B** correctness 0.8660 ต่ำกว่าเกณฑ์ 0.8663 เล็กน้อย, และไม่มีตัวชี้วัดใดดีขึ้น (งดตอบถูกเท่าเดิม, คำตอบว่างเพิ่ม) → ไม่ผ่าน; **C** correctness ลด 0.046 → ไม่ผ่าน ทั้งสองชุด (v2 และ v3) ไม่ผ่านกติกา จึง **หยุด ไม่รัน test และไม่ใช้ใน demo** ระบบที่ส่งมอบยังเป็น `frozen_v1` (+ โปรไฟล์ N8 ใน demo)
- **สิ่งที่เรียนรู้:** ปัญหาที่เหลือ (ตาราง, ตอบไม่ครบ, ประชากรไม่ตรง) แก้ด้วย prompt และ validator ไม่ได้ผลบน dev; การใส่หัวตารางและกฎเพิ่มทำให้ทั้งตอบว่างและปฏิเสธผิดเพิ่มขึ้น (rules ยาวขึ้น ทำให้โมเดลงดตอบหรือถูก validator ตัดมากขึ้น) สาเหตุรากของตารางอยู่ที่การแตก chunk (เช่น q141: หน่วย "ต่อ 100 กรัม" อยู่คนละ chunk กับแถวตัวเลข) ต้องแก้ที่ chunking/ดัชนี ซึ่งเป็นงานของ Track B และต้องสร้างดัชนีใหม่ ไม่ทำในรอบนี้
- **ประชากรไม่ตรง (q157):** ตัวตรวจกลุ่มประชากรเป็นกฎที่ใช้ได้ แต่ไม่ได้ทดสอบกับ q157 เพราะอยู่ใน test ซึ่งไม่แตะ บน dev การงดตอบถูกกับข้อไม่มีคำตอบไม่ดีขึ้น (8/9 และ 7/9 เท่าเดิม) จึงไม่มีหลักฐานว่าได้ผล ตัวตรวจยังเป็นตัวเลือกปิดในโค้ด (`validator_population`)
- **ข้อควรระวังในการตีความ:** ทั้งหมดเป็น judge เดียว ความต่างระดับ ±0.03 อยู่ในความแปรปรวนของ judge (ข้อ 5) และ dev มี 97 ข้อ ผมไม่ได้สรุปว่า "v2/v3 ทำให้แย่ลงอย่างมีนัยสำคัญ" แต่ว่า "ไม่ผ่านกติกาการรับที่ประกาศไว้ก่อน"

- **ทางแก้ที่ไม่ได้ลองเพราะตัวเลขไม่คุ้ม:** ขยายหลักฐานด้วย chunk ข้างเคียง (±1 ในเอกสารเดียวกัน) ของ top-5 ตรวจแบบออฟไลน์ (ไม่เรียก LLM): ข้อที่หน้าเฉลยไม่ติด top-5 มี dev 7 ข้อ และ test 6 ข้อ แต่ chunk เฉลยเป็นข้างเคียงของ chunk ใน top-5 เพียง **1 ข้อต่อชุด** การขยายจึงไม่ช่วยส่วนใหญ่ของที่ค้นพลาด และจะเพิ่ม token จึงไม่ลอง
